[1] الرؤية المعمارية والهدف الأساسي للمنظومة (Architectural Vision)
----------------------------------------------------------------------------------------
1. قناة يوتيوب الرسمية المستهدفة:
   https://www.youtube.com/channel/UClncV9OLPto_MinRzGfjr2g/videos
   تحتوي على 2,407 مقاطع فيديو، منها 2,371 تلاوة قرآنية نقية (بعد الفلترة الصارمة واستبعاد
   مقاطع Shorts الدعائية والخطب والدروس المنبرية).

2. العزل التام في وقت التشغيل (Strict Runtime Isolation):
   - تطبيق "قرآني" على الهاتف (Android) وعلى التلفاز (Android TV) يعتمد اعتماداً حصرياً
     وقاطعاً 100% في وقت التشغيل على منصة Archive.org فقط.
   - رابط الفهرس الوحيد الذي يطلبه التطبيق عند الدخول لشاشة الشيخ ياسر الدوسري:
     https://archive.org/download/qurani-yasser-aldosari-prayers/aldosari_prayers.json
   - ممنوع منعاً باتاً تحت أي ظرف جعل التطبيق يعتمد وقت التشغيل على GitHub أو على بروكسيات
     أو سحب مباشر من يوتيوب، وذلك لضمان سرعة الاستجابة ومنع حظر الـ IP أو استهلاك الموارد.
   - سلوك عدم الاتصال (Offline Resilience): في حال تعذر الوصول لأرشيف أو انقطاع النت،
     يعرض التطبيق فوراً التلاوات المخزنة بالكاش والملفات المدمجة (R.raw.radio_moshafs)
     بشعار "يعرض الموجود" دون أي تعطل أو شاشات فارغة.

3. المعايير الصارمة لأسماء التلاوات (Dignified Titles):
   - التلاوات تُرفع وتُعرض بأسماء قرآنية وقورة وواضحة فقط، مستخرجة برمجياً:
     [اسم السورة أو الآيات] - [الصلاة والتاريخ الهجري] - الشيخ د. ياسر الدوسري
   - استبعاد جميع العناوين الدعائية وأساليب جذب المشاهدات الخاصة بيوتيوب.

[2] المنظومة السحابية المعتمدة (Approved Production Architecture)
----------------------------------------------------------------------------------------
تعمل المنظومة السحابية بالكامل عبر GitHub Actions بدون استهلاك أي باقة أو وقت من الجهاز:

1. عزل الرفع إلى Archive.org عن تغيير الـ IP (حماية حساب أرشيف):
   - خوادم Archive.org (S3 API) تحظر وترفض عمليات الرفع الكثيفة القادمة من شبكات VPN
     أو البروكسيات العامة وتصنفها كـ Spam أو تفرض خطأ 403 Forbidden.
   - لذلك: تم عزل عملية الرفع بالكامل؛ حيث يتصل سكريبت الرفع (uploader.py / ia upload)
     بشكل مباشر 100% عبر شبكة السيرفر الطبيعية دون المرور بالنفق.

2. بروكسي محلي معزول لـ YouTube فقط (Cloudflare WARP in Proxy Mode):
   - خوادم مايكروسوفت (Azure Datacenters) التي تستضيف GitHub Actions محظورة سلفاً من
     يوتيوب وتواجه مباشرة خطأ "Sign in to confirm you're not a bot" أو HTTP 429.
   - الحل المعتمد: تثبيت عميل Cloudflare WARP الرسمي وتشغيله بوضع البروكسي المحلي فقط:
     warp-cli --accept-tos mode proxy
     warp-cli --accept-tos proxy port 40000
     warp-cli --accept-tos connect
   - يتم توجيه أداة (yt-dlp) فقط إلى هذا البروكسي:
     yt-dlp --proxy socks5://127.0.0.1:40000
   - هذا يمنح تحميلات يوتيوب عنوان IP مستقلاً ونظيفاً، بينما تظل بقية اتصالات السيرفر
     (Archive.org و GitHub Git) تعمل عبر شبكتها الرسمية الأصلية بأمان تام.

3. بروتوكول تطبيق أندرويد وتخطي صفحات الويب:
   - يتم تمرير المعاملات التالية لـ yt-dlp:
     --extractor-args "youtube:player_client=android;player_skip=webpage,configs"
   - هذا يلغي طلب صفحة الويب (HTML Webpage) التي تسبب الـ 429، ويخاطب خوادم يوتيوب
     بواجهة تطبيق الموبايل الرسمية.

4. نظام الدفعات المتسلسلة (Batch & Auto-Chain Architecture):
   - حجم الدفعة المعتمد: 25 إلى 50 تلاوة في كل تشغيلة (تستغرق حوالي 12-20 دقيقة).
   - الفاصل الزمني بين كل فيديو والآخر: 3 إلى 5 ثوانٍ لتجنب الرقابة اللحظية.
   - السلسلة التلقائية (Auto-Chain): عند انتهاء الدفعة بنجاح ورفع الفهرس، يستدعي السيرفر
     الدفعة التالية تلقائياً عبر:
     gh workflow run "Cloud Bulk Sync (Zero Local Bandwidth)" -f limit=50 -f workers=2
   - هذا يضمن أن كل دفعة تعمل على آلة افتراضية جديدة تماماً (Fresh VM) بعنوان IP جديد.
   - صمام أمان التهدئة (Cooldown): إذا واجهت الدفعة تقييداً (0 items synced)، تتوقف السلسلة
     تلقائياً وتدخل في فترة تهدئة حتى الموعد التالي للجدولة التلقائية.

5. الجدولة التلقائية الدورية (Hourly Cron Job):
   - الورك فلو مبرمج بـ Cron دوري: '0 * * * *' (كل رأس ساعة).
   - حتى في حال توقف السلسلة، يستأنف السيرفر العمل تلقائياً كل ساعة لسحب دفعة جديدة بهدوء.

[3] التجارب الفاشلة وأسباب فشلها الذريع (Post-Mortem: Failed Approaches)
----------------------------------------------------------------------------------------
يجب على أي مطور يتابع هذا المشروع تجنب الطرق الآتية التي أثبتت التجربة العملية فشلها:

1. الفشل الذريع الأول: الاعتماد على كوكيز المتصفح الشخصي (Browser Cookies) في السحابة:
   - الفكرة السابقة: استخراج cookies.txt من متصفح كروم محلي وحقنه في GitHub Secrets.
   - سبب الفشل: أنظمة الحماية في جوجل تكتشف فوراً عندما تُستخدم كوكيز حساب منزلي لإجراء
     مئات التحميلات المكثفة من عناوين مراكز بيانات سحابية (Microsoft Azure US).
   - النتيجة: يوتيوب يبطل صلاحية الكوكيز فوراً ويطلب كابتشا وتسجيل دخول جديد
     (Sign in to confirm you’re not a bot). الكوكيز لا تصمد في السحابة وتدخل في دوامة
     تجديد مستمر كل بضع ساعات.

2. الفشل الذريع الثاني: السحب المباشر بدون كوكيز وبدون بروكسي من خوادم GitHub:
   - الفكرة السابقة: جعل yt-dlp يسحب مباشرة دون كوكيز بالاعتماد على التحديث التلقائي.
   - سبب الفشل: يوتيوب يحظر نطاقات IP الخاصة بـ Microsoft Azure Datacenters بالكامل
     ويعطي فوراً HTTP 429: Too Many Requests أو يمنع التنزيل تماماً.

3. الفشل الذريع الثالث: توجيه شبكة السيرفر بالكامل عبر نفق WireGuard (wg-quick up wg0):
   - الفكرة السابقة: استخدام إضافات مثل fscarmen/warp-on-actions في وضع wireguard العام.
   - سبب الفشل:
     أ) خوادم مايكروسوفت تسقط حزم UDP عبر المنفذ 2408، مما أدى لتعليق الـ Runner وانقطاع
        اتصاله مع خوادم جيت هاب وضياع المهمة.
     ب) مرور اتصالات الرفع إلى Archive.org عبر نفق VPN أدى لخطر تصنيف الرفع كـ Spam.
   - الحل البديل الناجح: استخدام وضع البروكسي المحلي فقط (SOCKS5 Proxy on 127.0.0.1:40000).

4. الفشل الذريع الرابع: محاولة سحب القناة كاملة دفعة واحدة (Single Monolithic Run):
   - سبب الفشل: تجاوز الحد الأقصى لوقت التشغيل المسموح في جيت هاب، واستثارة حظر يوتيوب
     بسبب السحب المتواصل لعشرات الجيجابايت في جلسة واحدة، وضياع كل التقدم إذا انقطع الاتصال.

5. الفشل الذريع الخامس: تشغيل أكثر من ورك فلو متزامن في نفس الوقت (Parallel Runs):
   - سبب الفشل: حدوث تعارض في ملفات قاعدة البيانات catalog.json و sync_state.json
     (Git Push Conflicts)، بالإضافة إلى مضاعفة عدد الطلبات في نفس اللحظة مما يعجل بالحظر.
   - الحل المعتمد: إلزام السيرفر بقيد:
     concurrency:
       group: cloud-bulk-sync
       cancel-in-progress: true

[4] خطوات وبروتوكول الرفع إلى Archive.org (Archive.org Pipeline)
----------------------------------------------------------------------------------------
1. مستودع التخزين (Archive.org Item Identifier):
   qurani-yasser-aldosari-prayers

2. مفاتيح الاعتماد (S3 Keys):
   - IA_ACCESS_KEY و IA_SECRET_KEY مخزنان في GitHub Secrets ومحقونان في ~/.ia كالتالي:
     [s3]
     access = <IA_ACCESS_KEY>
     secret = <IA_SECRET_KEY>

3. مواصفات كل تلاوة مرفوعة:
   - ملف الصوت: MP3 بجودة صوت نقية كاملة (--audio-format mp3 --audio-quality 0).
   - صورة الغلاف: ملف JPG عالي الدقة (HD Cover) يتم رفعه بنفس اسم ملف الصوت إلى جواره.
   - الميتاداتا المرفقة مع كل ملف:
     * title: العنوان القرآني الوقور المستخرج.
     * creator: الشيخ د. ياسر الدوسري
     * mediatype: audio
     * collection: opensource_audio
     * language: ara
     * date: التاريخ الهجري والميلادي المستخرج.
     * subject: القرآن الكريم; تلاوات الحرم المكي; الشيخ د. ياسر الدوسري; صلوات الحرم

4. ملف الفهرس الرئيسي (aldosari_prayers.json):
   - بعد انتهاء كل دفعة، يقوم سكريبت generate_collections.py ببناء ملف الفهرس الموحد.
   - يُرفع الملف مباشرة إلى جذر المستودع على أرشيف:
     ia upload qurani-yasser-aldosari-prayers aldosari_prayers.json
   - هذا الملف هو العقد الرقمي بين الأرشيف وتطبيق الهاتف، وبمجرد تحديثه في أرشيف
     يصل التحديث لهواتف جميع المستخدمين تلقائياً عند فتح شاشة الشيخ.

[5] بنية ملفات المستودع ووظائفها (Repository Structure)
----------------------------------------------------------------------------------------
- .github/workflows/bulk_sync_cloud.yml:
  ملف الورك فلو الرئيسي لأتمتة السحابة بالكامل (تثبيت SOCKS5 WARP، تثبيت Deno و FFmpeg،
  إعداد مفاتيح أرشيف، تشغيل الدفعة، رفع الفهرس، عمل Git Commit & Push، وتشغيل الدفعة التالية).

- bulk_sync.py:
  المدير العام لتشغيل الدفعات عبر Threads متوازية، وحساب المتبقي، وفلترة المقاطع،
  وحفظ الإحصائيات في last_run_stats.json.

- youtube_sync.py:
  مسؤول عن التخاطب مع يوتيوب عبر yt-dlp، توجيه التحميل عبر البروكسي المحلي، استبعاد
  الشورتس والخطب، تنزيل الصوت والأغلفة، واستخراج التسميات القرآنية الوقورة.

- uploader.py:
  مسؤول عن الرفع الفعلي إلى Archive.org عبر S3، وإدارة ملفات الحالة sync_state.json
  و catalog.json وتوثيق روابط التحميل والاستماع.

- generate_collections.py:
  توليد ملف aldosari_prayers.json المتوافق تماماً مع محرك تشغيل تطبيق قرآني على أندرويد.

- requirements.txt:
  المكتبات المطلوبة: internetarchive, yt-dlp, requests.

[6] أوامر المطور للتشغيل والمتابعة اليدوية (Developer CLI Cheat Sheet)
----------------------------------------------------------------------------------------
1. تشغيل دفعة جديدة سحابياً في أي وقت:
   gh workflow run "Cloud Bulk Sync (Zero Local Bandwidth)" -R Mustafa-Elbheri/qurani-yaldosry-sync -f limit=50 -f workers=2

2. متابعة حالة التشغيلات السحابية:
   gh run list -R Mustafa-Elbheri/qurani-yaldosry-sync -L 5

3. قراءة اللوج المباشر لأحدث تشغيلة:
   gh run view <run_id> -R Mustafa-Elbheri/qurani-yaldosry-sync --log

4. فحص عدد ملفات الـ MP3 الحية على Archive.org:
   python -c "import urllib.request, json; r = json.loads(urllib.request.urlopen('https://archive.org/metadata/qurani-yasser-aldosari-prayers').read()); mp3s = [f for f in r['files'] if f['name'].endswith('.mp3')]; print('Total MP3s:', len(mp3s), 'Total Size GB:', round(sum(int(f.get('size', 0)) for f in mp3s)/(1024**3), 2))"

5. فحص عدد التراكات في ملف الفهرس الحي على أرشيف:
   python -c "import urllib.request, json; r = json.loads(urllib.request.urlopen('https://archive.org/download/qurani-yasser-aldosari-prayers/aldosari_prayers.json').read()); print('Catalog tracks:', len(r.get('tracks', [])))"
